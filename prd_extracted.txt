1. Product framing
Not: a Figma-to-React generator. Is: a browser-verified visual reverse-engineering compiler that generates code and iteratively optimizes it against a real Chromium render, measured against the original Figma design.
Lock-in rule #1:
The engine must never assume that Figma geometry directly equals CSS implementation. It must preserve observed geometry, infer implementation intent, evaluate the implementation in Chromium, and accept only validated improvements.
Lock-in rule #2:
Every optimization is reversible, measurable, scoped, and reproducible.
“Solid” definition: the engineering design is solid — deterministic, debuggable, measurable. Not a promise of 100% pixel-perfect output. Controlled benchmark target: 95%+.

4. Phase 1 — Deterministic Compiler
Goal: given one Figma frame, produce a real HTML/CSS render inside Chromium and get an honest, measured, reproducible score. Target here is pipeline correctness, not a high score.
Figma → Extractor → Parser → Design IR → HTML/CSS → Controlled Chromium  → DOM metrics → Reference comparison → Score
4.1 Reference Rendering Contract (mandatory, per benchmark frame)
Figma geometry and Figma rendered pixels are not the same thing. Before any comparison is trusted, freeze and record for every benchmark frame: - exact viewport width/height - exact export dimensions - device scale factor (DPR) - font environment (which fonts, which weights, source) - image assets used (exact files/hashes) - background (transparent vs. filled, and which color) - crop/export mode used to generate the reference image
The comparison engine consumes this contract as a fixed reference artifact — it does not re-derive it ad hoc per run.
4.2 Persistent node identity (Phase 1, not Phase 4)
Every NodeIR carries a stable identity from the very first parse, because Phase 2/3’s patch loop must re-recognize the same node across re-renders:
interface NodeIdentity {  figmaId: string;  internalId: string;  structureHash: string;}
Identity reconciliation rule: figmaId remains the stable source identity and internalId remains the logical IR identity. structureHash is recomputed after every committed structural patch. A structural patch must emit an identity-reconciliation record mapping affected pre-patch nodes to post-patch nodes; unchanged logical nodes retain their internalId. If a logical node cannot be deterministically mapped, the patch is rejected or the case is emitted as UNRESOLVED_SOURCE_AMBIGUITY.
4.3 Preserve component/instance identity now, infer abstraction later
Phase 1 preserves Figma’s native component/instance metadata as-is on the IR node (which component, which instance, which variant) — it does not attempt reusable React abstraction. That inference is Phase 4 (Structure Intelligence). Preserving the metadata now avoids an IR schema rewrite later.
4.4 Relative geometry from day one
For every node, compute both: - absolute geometry - geometry relative to its immediate parent
Rule: use relative geometry for diagnosis, absolute geometry for final visual verification. Without this, a parent shifted +20px makes every descendant look independently wrong, and the optimizer chases the wrong target.
4.5 Font/asset readiness precondition (non-optional)
No screenshot is taken until all of the following are true: - document.fonts.ready resolved - all images loaded - network idle / asset readiness confirmed
Screenshot-before-ready is not an acceptable shortcut, even in early prototyping.
Deliverables
figma-parser, design-ir (with NodeIdentity, relative geometry, preserved component metadata), code-generator (plain HTML/CSS only), renderer (Playwright/Chromium wrapper, enforces readiness precondition), geometry-engine + visual-engine (comparison v1), reference-artifact store per §4.1.
Exit criteria
Pipeline runs end-to-end on 3 benchmark frames (simple/medium/complex) and returns a real, reproducible score — the number itself can be 60–75% at this stage.

5. Phase 2 — Deterministic Optimizer (target: 90%)
Diff → Relative geometry → Ancestor-first diagnosis → Rule patch  → Same-browser evaluation → Commit / rollback
5.1 Mutation boundaries (explicit allow-list)
Canonical mutation authority: §16.4 is the normative mutation-boundary policy. This §5.1 table is a phase-level summary only; when rules differ, §16.4 governs.
Allowed
padding, gap, width, max-width, height, line-height
Restricted (needs strong evidence)
layout mode, component boundary, DOM structure, content, asset source
Forbidden by default
random absolute positioning, arbitrary transforms, full-tree rewrites
Rule: a patch must mutate the smallest possible ancestor/subtree that explains the diff.
5.2 Patch-based rollback (not full snapshots)
Do not snapshot the entire project per candidate. Store per patch: - forward patch - reverse patch - parent version reference - score before - score after
This keeps memory/IO bounded as the loop iterates.
5.3 Chromium reuse contract
Browser lifecycle:  1 browser process  1 reusable context  N candidate evaluations
Candidate isolation is mandatory: each candidate must start from the same committed version and must not inherit prior candidate state. CSS overrides are applied and reset; cookies, localStorage, sessionStorage, IndexedDB, Cache Storage, service workers, permissions, and other mutable browser state must be cleared, blocked, or recreated according to the benchmark runtime policy. Candidate B must never inherit Candidate A state. Any state reset failure invalidates the candidate evaluation.
Deliverables
root-cause-engine (diff → node → parent → ancestors, using relative geometry), optimizer (rule-based, enforces mutation boundaries), patch-engine (apply/measure/commit/rollback per §5.2), regression log of every patch attempt.
Exit criteria
≥ 90% average fidelity score across the full benchmark set, zero manual code edits between runs.

6.3 Responsive correctness — expanded definition
“No overflow” alone is insufficient; a page can pass that check and still be visually wrong. Responsive correctness must check: - overflow - collision - unexpected text wrap - unexpected component displacement - container instability - horizontal scroll - broken aspect ratio
Validated at 390 / 640 / 768 / 1024 / 1280 / 1440.
6.4 Dynamic content stress test — guardrail
Short/normal/long content injection may surface fixes like overflow: hidden or text-overflow: ellipsis. These are only acceptable when there is design evidence for them.
Rule: stress-test fixes must not override inferred/reference design intent without explicit evidence. A fix that merely hides overflow to “pass” the test, without matching how the design was actually meant to behave, is rejected.
Deliverables
layout-solver (type-specific candidate generator + evaluator per §6.1), optimizer extended with beam search (width 2–3) + caching (DesignHash, IRHash, Viewport, DPR, FontHash), responsive-engine + flow-engine (expanded checks per §6.3), benchmark report per frame per breakpoint, best-version guarantee per §6.2.
Exit criteria
≥ 95% average fidelity score at the primary breakpoint, and no unresolved instances of the §6.3 failure list across 390–1440px on at least the simple and medium benchmark frames.

7. Phase 4 — AI (reference only, not started)
Unresolved cases → AI  ├── intent inference  ├── composition  ├── root-cause reasoning  └── structured patch proposals→ Structure Intelligence → React → Tailwind → Production cleanup
AI consumes the unresolved case log (see §9 taxonomy) built up during Phase 2/3 — this becomes its trigger/training dataset, which is why the taxonomy is defined now rather than retrofitted later. Model-agnostic by design: engine value doesn’t depend on which LLM is plugged in.

8. Determinism — hardened definition
“Same input → same output” is only true if the environment is frozen. Determinism requires all of: - source (Figma file/frame version) - browser version - viewport - DPR - font files - assets - generator version - rule version - benchmark configuration
→ same output. Any of these drifting invalidates a reproducibility claim.

9. Unresolved case taxonomy (defined from Phase 2 onward)
Every case the rule optimizer / candidate search cannot resolve is logged under one of:
UNRESOLVED_LAYOUTUNRESOLVED_TYPOGRAPHYUNRESOLVED_ASSETUNRESOLVED_RENDERINGUNRESOLVED_RESPONSIVEUNRESOLVED_MAPPINGUNRESOLVED_SOURCE_AMBIGUITY
This taxonomy is the handoff contract to Phase 4 — it defines exactly what AI is being asked to solve, rather than “whatever the pipeline couldn’t do.”
Canonical mapping from the granular Phase 2/3 root-cause classes to these seven handoff buckets is defined in §16.1A and is normative for logging and AI routing.

12A. Phase 4 — Strong AI Architecture
Purpose. AI is a controlled escalation layer, not the primary renderer. The deterministic compiler, Chromium renderer, comparator, optimizer, and rollback system remain authoritative. AI proposes interpretations and patches; browser measurement decides acceptance.
12A.1 Model strategy
• Gemini: primary multimodal analyzer for screenshots, assets, OCR, and large visual context.
• OpenAI: complex layout reasoning, structured patch proposals, and difficult code-generation cases.
• Claude: code review, cleanup, refactoring, and visual-difference explanation.
• Groq: optional low-latency inference layer; quality depends on the vision model selected through it.
• The router must not call every model by default; escalate only when deterministic rules fail.
12A.2 AI routing
• UNRESOLVED_LAYOUT → Gemini, then OpenAI if confidence is low.
• UNRESOLVED_TYPOGRAPHY → OpenAI or Claude.
• UNRESOLVED_ASSET → Gemini.
• UNRESOLVED_RESPONSIVE → OpenAI, followed by multi-breakpoint browser validation.
• UNRESOLVED_MAPPING → Claude or OpenAI.
• UNRESOLVED_RENDERING → deterministic diagnosis first; AI only for explanation or a narrow hypothesis.
• UNRESOLVED_SOURCE_AMBIGUITY → human review by default; AI may propose evidence-backed interpretations, but no structural or semantic patch may be committed without explicit source evidence and deterministic validation.
12A.3 Structured patch contract
AI must return validated JSON and minimal patches, never an uncontrolled full-tree rewrite. Each proposal contains target node identity, property, old value, new value, reason, evidence, confidence, expected effect, and alternatives.
{  "targetNode": "hero-content",  "property": "gap",  "oldValue": "16px",  "newValue": "24px",  "reason": "Heading-to-paragraph spacing is smaller than the reference",  "confidence": 0.91}
12A.4 Acceptance and rollback
1. Validate every response against JSON Schema or Zod.
2. Apply the smallest patch to the identified node or ancestor.
3. Render only after fonts, images, and network assets are ready.
4. Measure fidelity and robustness before and after the patch.
5. Commit only when the relevant score improves without responsive regressions.
6. Rollback automatically when the score decreases, a regression occurs, or output is invalid.
12A.5 Confidence, disagreement, and caching
Determinism boundary: Phase 4 AI proposal generation is potentially non-deterministic, even when the environment and inputs are frozen. Caching and versioning make accepted/cached proposals reproducible; they do not imply first-call model determinism. Only the post-proposal acceptance, validation, scoring, rollback, and release pipeline inherits the deterministic contract.
• Record confidence and evidence for every AI inference.
• For high-impact decisions, obtain independent proposals from two models and test both as candidates.
• Cache by source hash, frame hash, viewport, DPR, font hash, asset hash, prompt version, and model version.
• Version prompts, schemas, adapters, and model configuration as production artifacts.
• Send low-confidence or repeatedly failing cases to a human-review queue.

12A.7 Phase 4 exit criteria
• AI is invoked only for logged unresolved cases.
• All model outputs pass schema validation.
• No accepted AI patch bypasses Chromium measurement or rollback.
• AI improves the deterministic baseline without reducing robustness.
• Fidelity and robustness are reported separately with model, prompt, and patch provenance.
12B. Updated product principle
The product is not an LLM wrapper. Its moat is the measurable reverse-engineering engine: Design IR, persistent node identity, relative geometry, controlled Chromium rendering, visual comparison, bounded search, responsive validation, and reversible patches. Models are interchangeable reasoning modules behind a strict implementation contract.
13. Sourcing & third-party reference policy
Purpose: several third-party tools and protocols (Figma MCP servers, existing Figma-to-HTML plugins, production design-to-code products) can accelerate specific packages below. This section defines exactly what may be reused, in what role, and under what constraint — so third-party code never quietly weakens the determinism guarantees in §8 or the AI containment rules in §12A.
13.1 Figma MCP servers (official or open-source) — Phase 1 data source only
Either the official Figma MCP server or a vetted open-source implementation may be used inside figma-client to fetch richer Figma data (variables, component/instance relationships, layout metadata) than the plain REST API exposes. This can improve the inputs to design-ir (§4.2, §4.3) but does not change the contract: every value pulled via MCP is still untrusted input that must pass through the Reference Rendering Contract (§4.1) and Chromium comparison before it affects a score.
If an open-source MCP implementation is forked, pin it to an exact commit hash and record that hash as part of the determinism inputs in §8 ("generator version"). Do not track a moving fork — an unannounced upstream change must not silently alter output for the same input.
13.2 Figma MCP in Phase 4 — evidence-only, not raw file access
MCP must not be used to give AI models open-ended access to the live Figma file during escalation. This would reintroduce "AI as primary interpreter," which §12A.1 and the unresolved-case taxonomy (§9) explicitly rule out. Instead, when a case is escalated, the ai-router passes only the frozen evidence for that specific case: the relevant NodeIdentity, relative-geometry diff, and screenshot crop. MCP-sourced Figma context may be used to pre-populate that evidence during Phase 1 extraction, not injected live into a Phase 4 prompt.
13.3 Existing Figma-to-HTML plugins (e.g. 10xHTML) — benchmark baseline only, not generator logic
Third-party Figma-to-HTML output may be used as a benchmark baseline: run it against the same benchmark frames (§4, §18) and report its fidelity/robustness scores alongside this engine's own, to demonstrate the deterministic pipeline's contribution. Its generation logic must not be forked into code-generator. That package's output is derived solely from design-ir per the mutation-boundary and patch-rollback contracts (§5.1, §5.2); importing a third party's independent heuristics would introduce an unaudited, non-reproducible component into a system whose core claim is deterministic and debuggable output.
13.4 Production design-to-code tools (e.g. Builder.io Visual Copilot, Figma Make) — architecture study only
Their published architecture, workflow, and stated approach to layout solving may inform the design of layout-solver (Phase 3) and design-intent-engine (Phase 4) as reference material. No code or proprietary model output from these products may be copied into this codebase. Where their approach conflicts with a lock-in rule in this PRD (§1) — for example, treating AI as the primary generator rather than a controlled escalation layer — this PRD's rule wins.
13.5 General reuse rule
Any third-party code, prompt template, or protocol client adopted under §13.1–§13.4 is versioned and pinned exactly like an internal package (§8). If it cannot be pinned to a specific, reproducible version, it may be used for research and architecture reference, but not compiled into a shipped package.

14.4 Figma extraction contract
Authentication is supplied through a secret outside source control. Tokens are never persisted in IR, logs, benchmark artifacts, or generated code.
Extractor recursively traverses the selected frame and preserves stable Figma IDs, component/instance metadata, paint/style data, layout data, text data, and asset references.
Every external asset is downloaded, hashed, validated, and mapped to a deterministic local asset path before code generation.
Extraction is versioned by parser version and Figma source version. A parser upgrade changes generator provenance and invalidates prior reproducibility claims.
Rate limits and transient API failures use bounded retries with exponential backoff. Permanent failures terminate the run with a typed error code.

14.9 Font and asset readiness contract
No screenshot is permitted until document.fonts.ready resolves, all referenced images report complete, and the page reaches the configured network/asset-ready state.
If the exact benchmark font is unavailable, the run fails with FONT_MISSING; silent substitution is prohibited.

Font and asset caches are content-addressed and immutable.

14.11 Visual, Compositing, Clipping, and Stacking Contract
Purpose. Phase 1–3 must treat visual effects and paint/compositing behavior as structured source data, not screenshot-only styling. Geometry correctness alone is insufficient for gradients, shadows, blur, masks, blend modes, clipping, or stacking order.
Rule: every supported visual feature is represented in canonical IR, deterministically compiled, rendered in the frozen Chromium environment, and accepted only after comparison. Unsupported or non-deterministic features must be reported explicitly as unresolved; they must never be silently replaced by a visually convenient approximation.
14.11.1 VisualIR
interface VisualIR {  fills: FillIR[];  strokes: StrokeIR[];  gradients?: GradientIR[];  shadows?: ShadowIR[];  blur?: BlurIR;  compositing?: CompositingIR;  clip?: ClipIR;  masks?: MaskIR[];  filters?: FilterIR[];  radius?: RadiusIR;  opacity: number;}
VisualIR is source-of-truth structure. Generated CSS/SVG is a derived representation and must not become the canonical state.
14.11.2 GradientIR
interface GradientIR {  type: "LINEAR" | "RADIAL" | "ANGULAR" | "DIAMOND";  stops: { position:number; color:RGBA; }[];  angle?: number;  center?: { x:number; y:number };  radius?: { x:number; y:number };}
Linear/radial gradients are mapped from measured Figma parameters. Stop order, stop positions, colors, angle/center, and bounds are preserved. Candidate search may adjust only explicitly permitted parameters when Chromium evidence shows a mismatch.
14.11.3 ShadowIR and EffectIR
interface ShadowIR {  type: "DROP" | "INNER";  color: RGBA;  offsetX:number;  offsetY:number;  blur:number;  spread?:number;}
Multiple shadows preserve source order. CSS box-shadow/text-shadow/filter mappings are selected from deterministic supported mappings; unsupported effect types become UNRESOLVED_RENDERING.
14.11.4 Blur, Filters, and Backdrop Effects
Blur must distinguish object blur, layer/filter blur, and backdrop blur because they produce different compositing behavior. The compiler must not substitute one for another merely because the screenshot is locally similar.
interface BlurIR {  type: "LAYER" | "OBJECT" | "BACKGROUND";  radius:number;}interface FilterIR {  type:string;  value:number|string;}
14.11.5 CompositingIR
interface CompositingIR {  opacity:number;  blendMode:string;  isolation:boolean;}
Blend mode, opacity, and isolation participate in visual correctness. A candidate that fixes geometry but changes compositing is a regression unless the reference evidence supports that change.
14.11.6 Clip and Mask Contract
interface ClipIR {  type: "RECT" | "PATH" | "RADIUS";  geometry?: unknown;}interface MaskIR {  type: "ALPHA" | "LUMINANCE" | "PATH";  referenceNodeId?: string;}
Clipping/masking must preserve containment semantics. overflow:hidden, clip-path, CSS masks, or SVG clipping are valid only when source evidence supports the corresponding behavior.
14.11.7 StackingIR
interface StackingIR {  position: "static" | "relative" | "absolute" | "fixed" | "sticky";  zIndex: number | "auto";  stackingContext: boolean;  paintOrder: number;}
The engine must explicitly model stacking context, z-index, DOM/paint order, and positioned descendants. Visual overlap is not considered solved merely because node geometry matches.
14.11.8 Visual Feature Capability Tiers
Tier A — deterministic CSS/SVG: supported when parameters map directly to a stable browser representation. Tier B — bounded approximation: allowed only when the approximation is represented explicitly, search space is bounded, and browser comparison validates improvement. Tier C — unresolved: used when no deterministic equivalent is available or the source behavior depends on unsupported rendering semantics.
Tier C cases must enter the unresolved taxonomy as UNRESOLVED_RENDERING, UNRESOLVED_ASSET, or UNRESOLVED_SOURCE_AMBIGUITY as appropriate. No hidden screenshot-tracing fallback is permitted.
14.11.9 Composite Visual Feature Handling
For nested effects such as gradient + image + overlay + blur + mask + shadow + absolute badge, the engine must evaluate the complete paint/compositing chain after deterministic structural compilation. The root-cause engine may then isolate the smallest node/ancestor responsible for the diff before generating a patch.
The implementation must preserve separation between layout correctness, paint correctness, compositing correctness, and stacking correctness so that a paint fix cannot silently mutate layout semantics.
15. Comparison and Scoring Specification
15.1 Screenshot normalization
Reference and candidate images must be normalized to identical pixel dimensions and DPR semantics before comparison. Alpha treatment, background, and color representation are taken from the reference artifact, never inferred independently during scoring.
15.2 Visual-diff algorithm
1. Validate dimensions and image metadata.
2. Normalize alpha/background according to the reference artifact.
3. Compute absolute per-pixel color error with an anti-alias tolerance.
4. Produce a binary error mask using the configured threshold.
5. Merge nearby error pixels into diff regions.
6. Compute region area, bounding box, severity, and nearest NodeIR ownership.
7. Produce a perceptual similarity score for large-area structural differences.
8. Persist raw diff artifacts and normalized metrics.
9. Never discard a diff solely because it is difficult to explain.
15.3 Geometry comparison
For each matched node:
  dx = candidate.x - reference.x
  dy = candidate.y - reference.y
  dw = candidate.width - reference.width
  dh = candidate.height - reference.height

Relative diagnosis uses:
  dxRel = candidate.relative.x - reference.relative.x
  dyRel = candidate.relative.y - reference.relative.y
  dwRel = candidate.relative.width - reference.relative.width
  dhRel = candidate.relative.height - reference.relative.height

Absolute geometry remains the final verification metric.
15.4 Fidelity score v1
The scoring mechanism is frozen for implementation, while weights remain benchmark-calibratable within a versioned scoring profile. Initial profile: Geometry 20%, Layout 20%, Typography 15%, Style 15%, Assets 10%, Perceptual Visual Diff 20%.
Fidelity =
  0.20 * Geometry +
  0.20 * Layout +
  0.15 * Typography +
  0.15 * Style +
  0.10 * Assets +
  0.20 * Perceptual

Each component is normalized to [0,100].
Final score is rounded to two decimals.
Score profile ID is recorded in every report.
Weights may change only by incrementing the scoring-profile version and recording the benchmark-based justification. Historical results remain tied to the profile that produced them.
15.5 Score acceptance rules
A candidate is eligible for commit only when:
  scoreAfter > scoreBefore + improvementThreshold
  AND no critical regression exists
  AND candidate is valid
  AND render completed under the readiness contract

Default improvementThreshold = 0.05 score points.
Critical regression = any hard responsive failure, missing required asset/font,
invalid DOM mapping, or material degradation in a protected region.
15.6 Robustness score
Robustness is reported separately and must never be averaged into Fidelity. It is computed across responsive and dynamic-content scenarios, with hard failures for overflow, collision, broken aspect ratio, horizontal scrolling, and other benchmark-defined critical defects.
Robustness report fields
- responsiveCoverage
- overflowViolations
- collisionViolations
- unexpectedWraps
- containerInstability
- horizontalScrollViolations
- aspectRatioViolations
- dynamicContentViolations
- robustnessScore [0,100]
- criticalFailures []

16. Optimizer Specification
16.1 Root-cause diagnosis algorithm
Input: diff regions + node ownership + relative geometry

1. Cluster nearby diff regions.
2. Map each region to affected nodes.
3. Walk from each affected node to its parent and ancestors.
4. Identify the smallest common ancestor that explains the error pattern.
5. Classify root cause:
POSITION | SIZE | GAP | PADDING | ALIGNMENT | TYPOGRAPHY | PAINT | GRADIENT | SHADOW | BLUR | CLIP_MASK | COMPOSITING | STACKING | TRANSFORM | CONSTRAINT | ASSET | CONTENT_FLOW | RESPONSIVE | UNKNOWN
6. Emit an evidence record containing before/after geometry and region coverage.
7. Generate only hypotheses permitted by mutation boundaries.

16.6 Beam search
Eligibility invariant: candidates are admitted to the beam only after §15.5 acceptance checks pass. A higher raw Fidelity score cannot outrank an ineligible candidate.
initialBeam = [initialVersion]
beamWidth = 3
maxIterations = 20

for each iteration:
  expand each version with deterministic candidates
  cheap-filter candidates using DOM/geometry constraints
  render survivors in Chromium
  score survivors
  keep the top beamWidth valid versions by:
    1. higher Fidelity
    2. higher Robustness when Fidelity ties
    3. lower patch count when both tie
    4. lexicographically smaller patch ID as final deterministic tiebreaker

return globally best observed version

17. Responsive and Dynamic Content Validation
17.0A Visual/Compositing Root-Cause and Candidate Rules
Visual effects follow the same ancestor-first diagnosis contract as geometry. A diff must be classified before a mutation is generated.
Diff pattern → candidate classColor-field mismatch → gradient/fill/opacitySoft halo mismatch → shadow/blur/filterWrong overlap → stacking/z-index/paint orderWrong visible boundary → clip/mask/radiusTransparent overlay mismatch → opacity/blend/isolationVector edge mismatch → SVG/path/stroke
Candidate generation is type-specific and bounded. For example, a gradient candidate may vary angle or stop position within configured deltas; a shadow candidate may vary blur/offset/spread within bounded deltas; a z-index candidate may test only a small deterministic set of relative stacking alternatives.
The optimizer must not add position:absolute, transform, overflow:hidden, or arbitrary z-index merely to reduce a screenshot diff. Such mutations require source evidence and must respect the mutation boundaries and responsive guardrails.
Every visual candidate follows: schema validation → mutation-boundary validation → readiness-gated Chromium render → Fidelity/Robustness measurement → commit or rollback.

No unstable container width/height behavior caused by optimizer patches.

30.1 Change-control rule
Any change that alters IR semantics, scoring, patch semantics, candidate ordering, rendering environment, benchmark interpretation, or AI contracts requires a versioned ADR or schema/rule version bump. This prevents accidental architectural drift.

31. Final Definition of Done
The project is considered implementation-complete for a phase only when all applicable conditions below are true:
All required schemas and package contracts are versioned and validated.
Benchmark fixtures exist for simple, medium, and complex tiers.
The deterministic environment is reproducible and recorded.
Unit, integration, golden visual, regression, failure-path, and end-to-end tests pass.
No accepted optimizer patch bypasses measurement, mutation boundaries, or rollback.
Every benchmark result has complete provenance and audit artifacts.
No manual source edits are required between optimization runs.
Unsupported inputs fail explicitly and are represented in the unresolved taxonomy where applicable.
Phase gates are executable through the CLI and return deterministic exit codes.
Phase 4 AI remains strictly subordinate to the deterministic acceptance system.
Security, credentials, resource limits, and data-retention rules are documented and enforced.
31.2 Final project principle
31.1 Visual Fidelity Definition of Done
Visual fidelity is not considered complete unless supported geometry/layout, gradients, fills/strokes, shadows/effects, blur, clipping/masking, opacity/blend modes, SVG/vector rendering, transforms/rotation, Figma constraints, and stacking/overlay behavior pass their dedicated benchmark fixtures or are explicitly classified as unresolved.
For every accepted visual patch, the audit trail must record the source visual feature, target NodeIdentity, before/after render evidence, candidate property, Fidelity/Robustness delta, and commit/rollback decision.
The deliverable is a deterministic, browser-verified reverse-engineering compiler with a controlled search-based optimizer and a bounded AI escalation layer. The implementation must optimize for measurable fidelity, reproducibility, debuggability, reversibility, and robust responsive behavior rather than screenshot-matching tricks or uncontrolled LLM generation.
32. Master Scope and Gap-Control Contract
32.1 Supported Design-Semantics Matrix
Phase 1–3 deterministic scope explicitly covers geometry, auto-layout, grid-like structures, typography/font readiness, assets, gradients, fills/strokes, shadows/effects, blur classes, opacity, blend/isolation, clipping, masks, SVG/vector, transforms/rotation, stacking/z-index/paint order, Figma constraints, responsive breakpoints, dynamic-content flow, and visual regression. Each capability must either have a deterministic mapping plus browser validation or be explicitly classified as unresolved.
32.2 No-Silent-Approximation Rule
The implementation may not silently replace unsupported or ambiguous Figma semantics with arbitrary absolute positioning, transforms, z-index values, overflow hiding, asset substitution, DOM rewrites, or fabricated visual effects. Every approximation must be source-supported, bounded, versioned, rendered, measured, and rollback-safe; otherwise the case enters the unresolved taxonomy.
32.3 Cross-Phase Contract
Phase 1 owns source extraction, canonical IR, deterministic rendering, and reference contracts. Phase 2 owns ancestor-first diagnosis and reversible bounded patches. Phase 3 owns deterministic candidate search, visual/compositing solving, responsive/constraint validation, and global-best selection. Phase 4 owns only unresolved-case interpretation and structured proposals; it never becomes the renderer of record.
32.4 Release Gate Completeness
A phase cannot be declared complete from Fidelity alone. The required gate must include applicable correctness, robustness, protected-region, unsupported-feature, determinism, audit-trail, and regression criteria. A benchmark result with an unexplained failure, environmental drift, or silent approximation is not a valid success.
32.5 Engineering Deliverable Boundary
This PRD is the authoritative product/architecture contract. Package-level engineering specifications may define algorithms, data structures, browser APIs, exact candidate deltas, and implementation mechanics only when they preserve the contracts here. Any change to semantics, scoring, candidate ordering, mutation boundaries, rendering environment, or AI authority requires a versioned ADR or schema/rule version bump.
Version v7 closes the identified cross-contract gaps in v6: reconciled mutation tiers, canonical root-cause taxonomy mapping, complete AI routing, explicit best-version eligibility, structural identity reconciliation, full candidate browser-state isolation, and an explicit Phase 4 determinism boundary.
